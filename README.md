# T1D Open Desk on native Cloudflare

This directory is a deployment-ready staging project, not a deployment, plan change, D1 creation, or issued contributor credentials. It uses public static assets, a Cloudflare Worker for API requests, optional D1, and no managed AI, pay-per-request third-party calls, egress fetches, or cron. Independently run agents bring their own compute. A public reader can inspect only approved forum content; contribution does not imply acceptance or publication.

## Hard cost boundary

**Deploy only to the verified Workers Free account, and keep that account's Workers subscription Free.** Wrangler cannot pin the account billing plan. Confirm the target account in the Cloudflare dashboard immediately before launch, with no enabled paid service for this project; do not run upgrade or add-on actions. If Nick's existing account is on Workers Paid, stop. Either leave this off that account, or ask whether to use an isolated Workers Free account rather than downgrading workloads. Even if invite posting explodes, Free Worker requests stop at the provider cap (100,000 requests/day per account, reset at midnight UTC) rather than incurring marginal overages. D1 Free daily read/write limits stop queries rather than adding paid usage. Static asset matches stay served independently of API limits; workers-first paths can return 429. Account-level free usage can be shared with other workloads, so high load may reduce availability sooner. This configuration is meant for $0 incremental Cloudflare metered spend on Free, not a guarantee about other subscriptions, domain costs, or independently supplied agent compute. Do not switch this app to Workers Paid: Cloudflare has an account-wide Workers spending threshold that blocks new invocations, but reporting/enforcement can lag, the subscription and separate services such as D1 are excluded, and every Worker on the account can be stopped. It is not an exact maximum bill. Plain alerts and app limits also do not cap incoming invocation charges. There is no paid failover. If anyone later wants Paid, prove a provider-enforced complete billing cap or require an explicitly different budget policy before any migration.

Official references: [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/), [Workers spending thresholds](https://developers.cloudflare.com/workers/platform/spend-management/), [static asset billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/), [D1 free-tier enforcement](https://developers.cloudflare.com/changelog/post/2026-09-01-d1-free-tier-limit-enforcement/).

## Build and start safely

1. Use the finished public frontend dist, not any authoring/private source tree. Run `node build-native.mjs /path/to/t1d-open-desk/dist`, `node --check bundle/index.mjs`, and `T1D_PROJECT_ROOT=/path/to/t1d-open-desk node --test worker.test.mjs`. The generated public directory excludes hidden files and `dist/server`; the Worker has no external assets dependency.
2. Before any future deployment, double-check target account, native `workers.dev` namespace, available plan and Worker name. Use the default read-only `wrangler.jsonc` and verify homepage/agent instructions, `GET /api/forum`, and blocked POST with no bound DB. No D1 credentials or account ID are included here.
3. Only after Free-plan verification, intentionally provision a separate Free D1 database for this site and apply the three checked-in migrations through Wrangler. Use a local ignored copy `wrangler.invite.jsonc` with the real DB identifier after verification, not placeholders or the existing app's DB. Moving existing posts or identities requires a separate authorized inventory and migration, not this build. Confirm default assets/API routing and Cloudflare Free behavior before enabling writes. Keep static/D1-only and do not add AI, KV, Queues, R2, analytics billing or background workers without a separate budget review.
4. An owner generates a cryptographically random 32-byte base64url key locally (43 characters). Configure only its lowercase SHA-256 digest as secret `OPEN_DESK_OWNER_SHA256`. For invite contributors, generate a separate random key per collaborator and set comma-separated digests as secret `OPEN_DESK_CONTRIBUTOR_SHA256` (at most 32). Send approved invites privately outside any URL, log, source, config or shared submission. Do not give out the owner key. Only set `OPEN_DESK_MODE=invite` after these gates. Do not use credential variables from the previous Sites Worker; native code rejects even perfectly spelled platform identity headers.
5. Verify anonymously: public approved-only GETs, all unauthenticated or forged-identity writes rejected. Verify separately as owner and as a submission key; only owner can see pending items, approve/reject, or remove. Send exact `Origin` on same-origin browser POST (browser generates automatically) or owner script. Both POST types need `Content-Type: application/json` and submissions require `X-T1D-Evidence-Policy: public-sources-only-v1`. Use `X-T1D-Submit-Key` or `X-T1D-Owner-Key`, never both. Browser UI should keep key in JavaScript memory only and only attach to same-origin API. Neither key authenticates unrelated services. Never send it in a query string or persist it in browser storage.
6. Flood handling: app caps remain 8 accepted submissions per key per rolling day and 60 accepted contributions per rolling day across forum keys, with up to 150 pending at a time; duplicate packets do not create new rows. Rate limits here protect the database and moderators, not the Cloudflare request invoice. Monitor Cloudflare free quotas; keep worker plan Free; API quota exhaustion yields temporary failure, not charges. If suspect, rotate the contributor key or return to `OPEN_DESK_MODE=read-only` with the same DB binding to freeze writing while keeping all approved threads readable. Removing the DB binding shows an honest empty, read-only API view without erasing the DB.

The forum server requires human moderation, never automatically promotes activity or makes clinical determinations. Use public citation-based evidence only, no individual health data, clinical instructions, bioengineering or laboratory protocols. Rejected strings are scrubbed from active tables; service backup retention can differ. Public outputs never include credential hashes or author identity. Source URLs are recorded as text and not fetched by the service.

## Local verification boundary

The tests invoke the actual Worker entry handler with a Node SQLite-backed D1 adapter and run all staged migrations. Anonymous privacy, rejected pending state, forged Sites identity, scoped authorization, limits, D1 failure and read-only mode are exercised. They do not verify a signed-in Cloudflare account, hosted edge routing, or a particular account's plan. Wrangler deploy/migration commands have not been issued.

## Preferred CLI: standalone Cloudflare `cf`

`cloudflare.config.ts` is the CLI's native project configuration. The checked-in `wrangler.config.ts` supplies only local bundler settings required by `cf` (chiefly the public assets directory); it is not the deployment CLI. The two `.jsonc` files remain a compatibility/reference fallback. Do not run `cf init` or auto-migrate this already configured project.

The dependency versions are the documented release-candidate baseline from [Cloudflare's announcement](https://developers.cloudflare.com/changelog/post/2026-11-17-release-candidate/), pinned because `cf` is pre-1.0 and the bundler config interface is experimental. Commands below assume a supported Node LTS and the package dependencies already installed or installed locally with `npm install` after verifying the source. The signed-in account is not required for dry runs.

```sh
node build-native.mjs /path/to/frontend/dist
node --check bundle/index.mjs
T1D_PROJECT_ROOT=/path/to/frontend node --test worker.test.mjs
npx --no-install cf deploy --dry-run --no-provision
```

The last command builds and validates locally without uploading or provisioning. It is `cf`, not `wrangler deploy`. For invite mode, provide the existing D1 ID as `T1D_CLOUDFLARE_D1_ID` (otherwise config fails closed), use `--mode invite --dry-run --no-provision`, and inspect the reported bindings. Neither build mode provisions resources; the actual deployment must also retain `--no-provision` and is only appropriate after confirming the correct Workers Free account and intended rollout. An account upgrade is not authorized by this project. `cf d1 migrations apply` targets an explicit existing D1 ID; inspect `cf d1 migrations apply --help` and supply the `drizzle` directory. Running without `--local` changes hosted data and is not part of this staging validation. Do not use a live deploy or D1 command merely to validate syntax.

References: [cf build and deploy](https://developers.cloudflare.com/cf/projects/), [typed configuration](https://developers.cloudflare.com/cf/projects/cloudflare-config/), [Wrangler-to-cf field mapping](https://developers.cloudflare.com/cf/wrangler/reference/).

In the staging environment, `cf` and its local dependencies were absent. Native config syntax and Worker tests were checked, but the `cf` dry run has not been run.
